## 0b. 失联保护（已实现）与残余风险

**失联保护（原 R1，按用户选定的"数据变化超时"方案实现）**：`USER/rc.c` + `USER/rc.h`

- 原理：接收器与发射端失联后通常会把"最后一帧"原样重复发送（字节完全不变），而真实手柄即使不动、摇杆 LSB 也有 ±1 抖动。
- 判据：连续 `RC_STALE_TIMEOUT_MS`（默认 **1000ms**）收到的 4 个摇杆字节 + 2 个按键字节逐字节完全相同 → 判定失联，`RC_Feed()` 返回 0，`main` 立即 `Motor_StopAll()`；数据一变即恢复。
- 接入方式：[main.c](Core/Src/main.c) 的 `USER CODE` 区内，驱动条件变为 `PS2_ReadData(&ps2) && ps2.mode == 1 && RC_Feed(&ps2)`。
- **权衡**：操作手把摇杆按住完全不动超过 1s 也会被保护停车（动一下即恢复）。觉得误停就调大 `RC_STALE_TIMEOUT_MS`，但保护变弱。观测用 `g_rc_dbg`（`stale`/`unchanged_ms`/`protect_count`）。
- 覆盖不到的情况：若接收器失联后仍在"抖动"输出，或操作手一直在动，则检测不出来——那种场景需要 START 使能式急停。

**上电安全启动（`RC_STARTUP_ARM_MS`，默认 200ms）**

- 上电后**默认不驱动电机**；必须连续 200ms 读到"四个摇杆都在中心附近（±20 码值）"才使能输出（`g_rc_dbg.armed`）。
- 任意时刻收到**垃圾数据（四轴同时 0x00 或同时 0xFF，接收器欠压/失联时的典型值）→ 立即解除使能并停车**（`g_rc_dbg.reject_count` 累计），必须重新回中 200ms 才能恢复。
- 目的：挡住"接收器欠压回垃圾数据 → 固件把它当成满速指令 → 电机电流把电源拉垮 → 接收器更不正常"这个**自锁循环**，同时也防止上电窜车。

| # | 事项 | 说明 |
|---|---|---|
| R2 | `0x79` 全量模式尾包 | 参考实现在该模式下会在同一 CS 窗口内续读 12 字节。本驱动未启用压力模式，按 9 字节处理；若实测遇到包错位再补 |
| R3 | 个别第三方/无线接收器数字态仍报 `0x7x` 且摇杆全 `0xFF` | 会算出满速。可在 `main` 里加"四轴同时为 0xFF/0x00 视作无效"的兜底。当前未加，避免影响正常判定 |
| R4 | 无程序跑飞保护 | 未加 IWDG。若后续发现莫名死机，再加独立看门狗 |


## 1. 结论

**是代码问题，不是手柄或接线"坏"。** 有**至少三处互相独立**的确定性缺陷，任何一处都足以造成"推摇杆无响应"：第 1 条（ID 判据用错下标）直接解释了"红灯模式无响应"，第 5 条（每字节切 CS，整包被手柄丢弃）是独立的第二重原因，第 4 条（PWM 15.26Hz / 1.5% 占空比）决定了"即使手柄读通了电机也不会转"。

## 2. 现场定位（为什么恰好是红灯模式无响应）

标准读取包 `01 42 00 00 00 00 00 00 00` 的**第 2 个返回字节是模式/型号 ID**：

| 返回值 | 含义 |
|---|---|
| `0x41` | 数字模式（绿灯，摇杆数据无效） |
| `0x42` | 部分第三方手柄 |
| `0x73` | 模拟模式（红灯） |
| `0x79` | 模拟全量模式（含按键压力值） |

`USER/ps2.c:113` 写的是：

```c
if (buf[1] != 0x5A && buf[1] != 0x41)
    return 0;  // 通信失败
```

`0x5A` 是 **0x42 轮询响应的第 3 个字节（`buf[2]`，"数据就绪"标记）**，同时也是退出配置命令的发送填充值；它 **不是 `buf[1]`**。原实现把下标 2 写成了 1，于是：

- 红灯模拟（`0x73`）→ 判定"通信失败" → `PS2_ReadData()` 返回 0
- `main.c:138-142` 走 else → 每次循环 `Motor_StopAll()`
- 结果：**摇杆怎么推都没反应**（完全符合现象）

而数字模式 `0x41` 反而通过了检查。

## 4. 修复方案 A：PS2 驱动（替换 `USER/ps2.c` 主体）

要点：**一包一个 CS 窗口** + **正确的 ID/mode 判定** + **正确的位序** + **包间隔 ≥1ms**。

> 下面这段是诊断当时的示意版本；**权威实现以 `USER/ps2.c` 为准**（已含包间隔 `PS2_PKT_DELAY_US`、
> `enable_rumble`/`set_bytes_large` 振动配置、上电握手 `HAL_Delay(50)`+两次空读、
> `g_ps2_dbg.init_ok`、按键字节序修正等后续补充）。

```c
#include "ps2.h"

/* 时序：参考实现 CTRL_CLK=4~5us；长线/电平裕量不足时可放大到 10us */
#define PS2_CLK_US        5
#define PS2_BYTE_DELAY_US 10

static void delay_us(uint32_t us)
{
    uint32_t start = DWT->CYCCNT;
    uint32_t ticks = us * (SystemCoreClock / 1000000U);
    while ((DWT->CYCCNT - start) < ticks) { }
}

static void DWT_Init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    DWT->CYCCNT = 0;
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;
}

static void PS2_CS_Low(void)  { HAL_GPIO_WritePin(PS2_CS_PORT,  PS2_CS_PIN,  GPIO_PIN_RESET); }
static void PS2_CS_High(void) { HAL_GPIO_WritePin(PS2_CS_PORT,  PS2_CS_PIN,  GPIO_PIN_SET);   }
static void PS2_CLK_Low(void) { HAL_GPIO_WritePin(PS2_CLK_PORT, PS2_CLK_PIN, GPIO_PIN_RESET); }
static void PS2_CLK_High(void){ HAL_GPIO_WritePin(PS2_CLK_PORT, PS2_CLK_PIN, GPIO_PIN_SET);   }
static void PS2_DO_Low(void)  { HAL_GPIO_WritePin(PS2_DO_PORT,  PS2_DO_PIN,  GPIO_PIN_RESET); }
static void PS2_DO_High(void) { HAL_GPIO_WritePin(PS2_DO_PORT,  PS2_DO_PIN,  GPIO_PIN_SET);   }
static uint8_t PS2_DI_Read(void) { return HAL_GPIO_ReadPin(PS2_DI_PORT, PS2_DI_PIN); }

/* 置DO -> CLK拉低 -> 采样DI -> CLK拉高；LSB first */
static uint8_t PS2_Transfer(uint8_t tx)
{
    uint8_t rx = 0;
    for (uint8_t i = 0; i < 8; i++) {
        if (tx & 0x01) PS2_DO_High(); else PS2_DO_Low();
        tx >>= 1;

        PS2_CLK_Low();
        delay_us(PS2_CLK_US);
        if (PS2_DI_Read()) rx |= (uint8_t)(1u << i);
        PS2_CLK_High();
        delay_us(PS2_CLK_US);
    }
    PS2_DO_High();                       /* 空闲保持高 */
    delay_us(PS2_BYTE_DELAY_US);
    return rx;
}

/* 关键：整包在同一个 CS 低电平窗口内完成 */
static void PS2_SendPkt(const uint8_t *tx, uint8_t *rx, uint8_t len)
{
    PS2_CS_Low();
    delay_us(PS2_BYTE_DELAY_US);
    for (uint8_t i = 0; i < len; i++)
        rx[i] = PS2_Transfer(tx[i]);
    PS2_CS_High();
    delay_us(PS2_BYTE_DELAY_US);
}

void PS2_Init(void)
{
    static const uint8_t enter_cfg[5] = {0x01,0x43,0x00,0x01,0x00};
    static const uint8_t set_mode[9]  = {0x01,0x44,0x00,0x01,0x03,0x00,0x00,0x00,0x00};
    static const uint8_t exit_cfg[9]  = {0x01,0x43,0x00,0x00,0x5A,0x5A,0x5A,0x5A,0x5A};
    uint8_t rx[9];

    DWT_Init();
    PS2_CS_High(); PS2_CLK_High(); PS2_DO_High();
    delay_us(200);

    for (uint8_t retry = 0; retry < 3; retry++) {
        PS2_Data_t d;
        PS2_SendPkt(enter_cfg, rx, sizeof(enter_cfg));
        PS2_SendPkt(set_mode,  rx, sizeof(set_mode));
        PS2_SendPkt(exit_cfg,  rx, sizeof(exit_cfg));
        if (PS2_ReadData(&d) && d.mode == 1)     /* 已进入模拟(红灯)模式 */
            break;
    }
}

uint8_t PS2_ReadData(PS2_Data_t *data)
{
    static const uint8_t poll[9] = {0x01,0x42,0x00,0x00,0x00,0x00,0x00,0x00,0x00};
    uint8_t buf[9];
    uint8_t id;

    if (!data) return 0;
    PS2_SendPkt(poll, buf, sizeof(poll));

    id = buf[1];
    if (id != 0x41 && id != 0x42 && id != 0x73 && id != 0x79)
        return 0;                                /* 无手柄 / 通信异常 */

    data->buttons = (uint16_t)((uint16_t)buf[3] << 8 | buf[4]);
    data->mode    = ((id & 0xF0) == 0x70) ? 1 : 0;

    if (data->mode) {
        data->right_x = buf[5];
        data->right_y = buf[6];
        data->left_x  = buf[7];
        data->left_y  = buf[8];
    } else {
        /* 数字模式摇杆无效，强制回中，配合 main 的 mode 判断做双保险 */
        data->right_x = data->right_y = data->left_x = data->left_y = 0x80;
    }
    return 1;
}

/* 可选：振动（需手柄支持并已开启振动功能，第三方手柄常无效） */
void PS2_Vibrate(uint8_t motor1, uint8_t motor2)
{
    uint8_t rx[9];
    uint8_t poll[9] = {0x01,0x42,0x00, (uint8_t)(motor1 ? 0x01 : 0x00), motor2, 0,0,0,0};
    PS2_SendPkt(poll, rx, sizeof(poll));
}
```

## 5. 修复方案 B：PWM 周期

现状：`PSC=71` → 计数时钟 1MHz；`ARR=65535` → 15.26Hz。目标：与 `motor.c` 的 1000 刻度一致，即 `ARR=999`（1kHz）。

**B1（推荐，CubeMX 重新生成不会丢）** —— 在 `USER/motor.c` 的 `Motor_Init()` 开头覆盖：

```c
void Motor_Init(void)
{
    /* 与 Motor_SetPWM 的 1000 刻度对齐：1MHz 计数时钟 / 1000 = 1kHz */
    __HAL_TIM_SET_PRESCALER(&htim2, 72U - 1U);
    __HAL_TIM_SET_AUTORELOAD(&htim2, 1000U - 1U);
    __HAL_TIM_SET_PRESCALER(&htim4, 72U - 1U);
    __HAL_TIM_SET_AUTORELOAD(&htim4, 1000U - 1U);
    htim2.Instance->EGR = TIM_EGR_UG;   /* 立即把 PSC/ARR 装入影子寄存器 */
    htim4.Instance->EGR = TIM_EGR_UG;
    /* ...以下保持原有 HAL_TIM_PWM_Start 循环... */
}
```

**B2（CubeMX 原生）** —— 在 CubeMX 中把 TIM2/TIM4 的 `Counter Period` 设为 `1000-1` 重新生成；
`.ioc` 对应新增 `TIM2.Period=1000-1`、`TIM4.Period=1000-1` 并加入各自 `IPParameters`，同时 `tim.c` 的 `Init.Period` 变为 `1000-1`。
注意：手工改 `.ioc` 有格式风险，建议在 CubeMX 界面里改。

两种方式二选一即可，不要叠加。

## 5b. 修复方案 C：麦轮逆解（缺陷 10）

原式把 `vx` 的系数写成了 RF/LR 为 `-1`，导致"推前进杆"输出的是对角差速。改为标准 X 型布局：

```c
// vx 的系数必须四个轮子全为 +1，否则"前进"会变成原地打转/斜移
speed_lf =  vx + vy_s + vw_s;   // 左前
speed_rf =  vx - vy_s - vw_s;   // 右前
speed_lr =  vx - vy_s + vw_s;   // 左后
speed_rr =  vx + vy_s - vw_s;   // 右后
```

三种基元动作的判据（也是软件自检的判据）：

| 输入 | 轮速模式 | 车体动作 |
|---|---|---|
| `vx=+1`，其余 0 | 四轮同向 `(+,+,+,+)` | 前进 |
| `vy=+1`，其余 0 | 对角配对 `(+,-,-,+)` | 平移 |
| `vw=+1`，其余 0 | 左右反向 `(+,-,+,-)` | 原地旋转 |

`vy`/`vw` 的正负极性取决于辊子朝向与电机极性，用 `MECANUM_STRAFE_SIGN` / `MECANUM_ROTATE_SIGN` 实测标定；`vx` 的符号没有这种自由度，必须四轮同号。

## 5c. 主机端回归测试

`tests/host_test.c` 用桩函数实现了一个"PS2 手柄模型"（CS 下降沿开始一包、CLK 下降沿采样 DO 并送出 DI、LSB first），
配合伪造的 DWT/CoreDebug 与假定时器实例，在 PC 上直接跑驱动与电机映射逻辑，无需硬件和 ARM 工具链：

```powershell
gcc -std=c11 -Wall -Wextra -DSTM32F103xB -DUSE_HAL_DRIVER `
    -ICore/Inc -IDrivers/STM32F1xx_HAL_Driver/Inc -IDrivers/STM32F1xx_HAL_Driver/Inc/Legacy `
    -IDrivers/CMSIS/Device/ST/STM32F1xx/Include -IDrivers/CMSIS/Include -IUSER `
```

## 6. 硬件侧需确认（不属于代码）

1. 接收器供电：建议 3.3V 且与 MCU 共地；5V 供电会让 DAT 输出 5V 电平。
2. 接线方向：PB12 = `DAT`（手柄→MCU，输入上拉），PB13 = `CMD`（MCU→手柄，输出）；接反会互相顶。
3. `PS2_CLK`：建议开漏 + 上拉（或串 1kΩ），手柄会拉低 CLK 做 ACK，纯推挽存在竞争风险。
4. HSE 晶振是否起振：若卡在 `Error_Handler()`，表现同样是"什么都不动"。

## 7. 验证步骤（建议顺序）

1. **先验证电机**：架空车体，把 `USER/motor.h` 的 `MOTOR_SELFTEST_ENABLE` 置 1 后编译烧录。上电会依次让 LF/LR/RF/RR 各正转 1s、反转 1s（调试器里看 `g_motor_testing` 可知当前测的是哪个轮子）。确认只有对应轮子转动、且"正转"方向与预期一致；测完把宏置回 0。
2. **再验证手柄**：在 CLion 调试器的 Watch 里加 `g_ps2_dbg`。红灯模式下应看到 `id=0x73`、`valid=1`、`ok_count` 递增、`raw[5..8]` 随摇杆变化（中心 ≈ `0x7F/0x80`）。若 `id` 恒为 `0xFF`、`ok_count` 不增长，则代码路径已通，问题在硬件侧（供电/接线/时钟），见第 6 节。
3. **最后接麦轮映射**：小占空比试车。先验证"前进走直线"（若原地打转，说明 vx 系数问题没改干净），再按第 5b 节标定 `MECANUM_STRAFE_SIGN` / `MECANUM_ROTATE_SIGN` 与死区。
4. **验证失联保护**：把 `g_rc_dbg` 加进 Watch。正常推杆时 `stale=0`、`unchanged_ms` 不断被清零；把手柄**电池拔掉/关机**（或按住摇杆完全不动 1s 以上）后，`stale` 应变 1、`protect_count` 加 1、车立即停；再动一下摇杆应立刻恢复。

## 9. 供电异常结案（2026-10-14）

**第十二次实测（结案）**：换一块新开发板后，**用同一个降压模块供电，两颗灯正常亮起**；实测降压模块**带载输出 ≈ 5.0V**（合格）。

→ **电源链（电池 → 降压模块 → 5V）合格，坏件是旧开发板本身**：其 3.3V 轨/LDO 已劣化 —— 表现为灯比 USB 供电时暗、空载灯亮但整体偏暗、最终"重新烧录后接电源电源灯都不亮"。旧板**退役**，不再用于比赛车。

→ **第十一次"负载在线束本身"的结论作废**：当时"只多 1~2mA 就翻车"本身就是**临界**特征，用旧板 LDO 带载能力不足即可解释；线束并未被证实有短路（但插到新板前仍建议量一次电阻作保险）。

→ **经验教训**：
1. 同一供电下**换板即恢复**，应首先怀疑板子本身；
2. 板载 LDO 的压差与带载能力差异很大，**输入偏低（如 5V 只有 4.5V）时不同板子表现完全不同**；
3. "空载正常、一加负载就塌"不一定指外部短路，也可能是**供电/稳压器已到带载极限**；
4. 用 `BRINGUP_HALT_LEVEL` 分档 + 量电流，是区分"电源带载不足"与"引脚短路"最快的办法。

> 说明：下面第 10 节按时间顺序保留了整个排查过程（含若干后来被推翻的中间结论），结案结论以本节为准。

## 10. 附录：供电异常排查（接收器/STM32 指示灯同时变暗 + PS2 掉线）

**实测记录（2026-10-14）**：麦轮的前进/自转/斜移全部验证正常后，某次上电出现"接收器电源灯与 STM32 板指示灯同时变暗、PS2 连接中断"。

**初步结论**：两个不同模块的指示灯同时变暗 = **共同电源被拉垮**，属供电/接线问题；PS2 掉线与 MCU 复位都是欠压的**结果**而不是原因。

**已排除**：自检宏（`MOTOR_SELFTEST_ENABLE=0`，且固件符号表里没有 `g_motor_testing`），故上电时固件不会主动驱动电机（`Motor_Init` 把所有 PWM 比较值置 0）。

**关键追加实测**：**一直按住 NRST 时两个指示灯持续正常亮，一松开就立刻变暗**；灯暗期间电机不转、DRV8833 与电机都不发烫。

→ **结论修正：MCU 一执行代码就把电源拉垮，负载在"逻辑侧"而不是电机侧。** 两种可能：

| 可能 | 说明 | 判别 |
|---|---|---|
| **A. 某个"上电即被驱动"的引脚短路/对顶** | `MX_GPIO_Init` 会把 PB13(DO) 拉低、PB14(CS)/PB15(CLK) 拉高；`MX_TIM2/TIM4_Init` 把 PA0-3、PB6-9 配成复用推挽输出（占空比 0 → 输出低）。这些线一旦对地/对电源短路，或与接收器/驱动的输出对顶，就会持续吃电流 | 运行电流比"按住复位"时高出**几百 mA** |
| **B. 3.3V 供电/稳压路径带载能力已损坏** | MCU 停在复位时电流很小 → 正常；一旦运行（约 40–50mA）+ 接收器就撑不住 | 运行电流只高几十 mA，但 3.3V 轨明显下跌 |

**测量方法**：万用表串在电源入口，分别记录"按住 NRST"与"松开运行"两种状态下的**总电流**和 **3.3V 轨电压**。

**决定性收窄（第三次实测）**：把**所有负载全部拔掉**，只留电池 + 降压模块，指示灯仍然不正常。

→ **故障锁定在"电池 → 连线/电池座/开关 → 降压模块"这条链里**，与 MCU、接收器、电机驱动、代码全部无关（它们已被物理断开）。前面看到的"MCU 一运行就掉压"只是**结果**：上游电压本就没稳住，负载电流一上来就被拉得更低。

**已确认拓扑**：2S 18650（7.4V）→ 固定输出 5V 的 DC-DC 降压模块。输入裕量约 2.4V，**充足** → "输入裕量不足"排除。

**第四次实测**：电池组空载电压**正常**（6.0–8.4V）；电池为"**每节 18650 内置保护板 + 普通电池盒**"。

→ 排除"电池完全没电/整组跳闸"，但**空载正常 ≠ 带载正常**。重点转向"带载压降"。

**决定性测量**：在"灯暗、模块接着"的状态下，**同时**记录三个电压（黑表笔固定电池负极）：

| 测点 | 判据 |
|---|---|
| ① 电池组两端（直接点在电池正负极） | 带载时就从 7V+ 掉到 3–4V → 电池内阻大或某节保护板动作 |
| ② 模块输入端（IN+/IN−） | ①正常但②明显低（差 >0.5V）→ 压降在电池盒弹片/开关/插头/线 |
| ③ 模块输出端（OUT+/OUT−） | ①②都 ≈7V+ 而③只有 1–2V → **模块损坏或输出侧短路** |

| 可能 | 说明 | 验证 / 修法 |
|---|---|---|
| **1. 电池盒弹片/正极凸点接触电阻**（普通电池盒最常见） | 空载电压正常，一带载（模块约 50–150mA）就大幅下跌；带保护板的加长电芯在普通盒里常顶不到 | 灯暗时同时量①与②；轻晃/压紧电池看电压跳变 → 换盒或补焊 |
| **2. 某节内置保护板先触发过流/过放保护** | 两节各自带保护板串联的经典故障：一节先跳 → 带载即断，空载仍有虚电压 | 分别量每节电芯；放到充电器上充一下（多数保护板靠充电复位） |
| **3. 降压模块损坏** | 输入 7–8V 正常，输出只有 1–2V | 用充电宝/实验室电源给模块**输入**供电（≥6V），看输出是否恢复 5V |
| **4. 模块输出侧短路**（线束/分电板焊锡桥） | 模块一直处于限流/打嗝保护，指示灯暗 | 断电拔电池，电阻档量模块输出端正负（含线束/分电板）→ 接近 0Ω 即短路 |

**2S 电池组的常见坑**：自己装的电池盒容易出现"某节接触不良/一节先放空"；带内置保护板的 18650 长度更长，普通电池盒的正极弹片可能压不到；XH2.54/JST 插头压接不良也是高频故障点。充电请用平衡充，别让单节长期低于 2.5V。

**第五次实测（关键提醒）**：电池组空载 **6.5–7.0V**；模块**输入端**与电池几乎相同；模块**输出端 ≈5V**。但这三个数都是**空载**量到的。

→ 万用表输入阻抗约 10MΩ、只取几微安，**空载 5V 是"虚电压"，不能证明模块能带载**。当前症状是"空载全正常、一加负载就塌"，所以必须做**带载测量**：

| 测试 | 做法 | 判据 |
|---|---|---|
| **A. 带载三点测量** | 接上 STM32 板（或其他已知负载），在"灯已变暗"时**同时**量 电池 / 模块输入 / 模块输出 | 电池掉到 3–4V(组) → 电芯内阻或电池盒接触；电池稳但模块输出掉 → 模块带载能力不足或掉出稳压区（6.8V 输入、5V 输出只剩 ~1.8V 裕量） |
| **B. 假负载测试** | 断开所有负载，在模块输出接一个 **47Ω/2W**（≈100mA）或 **100Ω/1W**（≈50mA）电阻，量输出是否仍 ≈5V | 输出塌下去 → **模块损坏/带载能力不足**；仍稳稳 5V → 模块没坏，问题在电池那一路或下游接线 |
| **C. 充满再测** | 把两节充到 4.2V/节（8.4V），重测 | 恢复正常 → 根因是电量偏低 + 内阻/接触；同时分别量两节看是否不平衡 |

**第六次实测（决定性）**：变暗的是 **STM32 板自己的两颗 LED**（电源灯 + 信号灯）；**把开发板里的程序擦除后，接 7.4V 电源，灯恢复正常**。

→ 与"按住 NRST 正常、松手变暗"完全一致：**只要 MCU 真正执行这份固件，板子的 3.3V 就被拉垮**。空白芯片时引脚高阻、主频低，所以正常。

**这不是"代码逻辑错"**：启动阶段固件并不驱动电机（`MOTOR_SELFTEST_ENABLE=0`，且上电安全启动还在等摇杆回中）。固件在启动时只有两件事会改变电流：

1. 把 MCU 切到 **72MHz** 并打开 GPIO/TIM 时钟（约 40–60mA）；
2. 把 11 个引脚（PA0-3、PB6-9、PB13/14/15）配成**推挽输出**并驱动。

因此只有两类根因，用一个电流数字即可分开：

| 观察（串万用表量 5V→板子的总电流） | 结论 |
|---|---|
| 运行比"空白/按住复位"只高 **30–60mA**，但 3.3V 掉到 1–2V | **电源侧**：板载 3.3V LDO 或 5V 路径带载能力已损坏，连 MCU 正常工作电流都供不上（代码无辜，换板或外部 3.3V 直供验证） |
| 运行比"空白/按住复位"高出 **200mA 以上** | **引脚侧**：某个被驱动的引脚对地/对电源短路，或与别的输出对顶（也是硬件问题，不是代码逻辑） |

**两分钟硬件排查（无需代码）**：断电拔电池，用电阻档逐个量被配置成输出的引脚**对 GND 的电阻**（PA0、PA1、PA2、PA3、PB6、PB7、PB8、PB9、PB13、PB14、PB15）。正常为几十 kΩ 以上；若某个脚只有几欧~几十欧，就是短路点（板子焊锡桥/排针/杜邦线/被轮子夹伤）。

**板上 LDO 验证**：拔掉模块的 5V 输入，用另一路稳定的 **3.3V 直接供到板的 3.3V 脚** → 若 MCU 与两颗 LED 都正常，则板上 LDO 已损坏。

**启动分步停机工具（已加入工程）**：`Core/Inc/main.h` 里的 `BRINGUP_HALT_LEVEL`（默认 0 = 正常运行）：

| 档位 | 停机位置 | 含义 |
|---|---|---|
| 1 | `HAL_Init` 后 | 仅内核 + SysTick |
| 2 | `SystemClock_Config` 后 | 已 72MHz，**引脚尚未被驱动** |
| 3 | `MX_GPIO_Init` 后 | PS2 四根线已配成 输入/输出 |
| 4 | `MX_TIM2/TIM4_Init` 后 | 8 路 PWM 引脚已配成复用推挽 |
| 5 | `PS2_Init` 后 | PS2 时序开始翻转 CLK/DO |
| 6 | `Motor_Init` 后 | PWM 通道已启动（占空比 0） |

用法：改数字 → 重新 build + 烧录 → 看灯亮度并量电流。**判读**：

- **档位 2 就已经变暗** → 与引脚/外设无关，纯电源/LDO 带载问题（代码无辜）；
- **档位 2 正常、3 或 4 变暗** → 引脚驱动导致的短路/对顶 → 用上面的对地电阻排查定位那一根；
- 5 或 6 才变暗 → 与 PS2 或 PWM 通道相关（进一步查接收器接线/驱动输入）。

> 测完记得把 `BRINGUP_HALT_LEVEL` 改回 0，否则板子会停在死循环里（按复位或重新上电即可恢复）。

**第七次实测（转折点）**：`BRINGUP_HALT_LEVEL = 2`（已 72MHz，但 **MX_GPIO_Init 之前、一个引脚都没驱动、PS2/电机代码都没执行**）→ **LED 亮度正常，接收器灯也正常亮起**。

→ **3.3V 电源链是好的**：它能同时带 72MHz 的 MCU 和接收器。**此前"板载 LDO 被打伤"的推断作废**，板子大概率没坏。
→ 故障发生在**引脚配置/驱动层**，即 `MX_GPIO_Init` 及之后。真实负载不是"MCU 工作电流"，而是某个**被驱动引脚上的短路/对顶**。

**下一步二分**（每档只改一个数字，重烧后拔掉 ST-Link 再上 7.4V）：

| 档位 | 停机位置 | 若此档开始变暗 |
|---|---|---|
| 3 | `MX_GPIO_Init` 后 | PS2 四根线（PB12 输入 / PB13/14/15 推挽输出）上有短路或对顶 |
| 4 | `MX_TIM2/TIM4_Init` 后 | PA0-3、PB6-9（8 路 PWM/驱动输入）上有短路；或驱动模块的供电误接到信号脚 |
| 5 | `PS2_Init` 后 | 真正开始通信（CS 拉低、CLK 翻转）才触发 → 典型是 **DAT/CMD 接反**（CS 高时接收器 DAT 高阻，所以档位 3 看不出来） |
| 6 | `Motor_Init` 后 | PWM 通道启动后触发（占空比 0，正常不应有电流） |

**配合"拔线"可把范围再缩小一半**（都停在档位 3 上试）：

| 试验 | 连接 | 若变正常说明 |
|---|---|---|
| A | 接收器 + 驱动都接着 | —（基准） |
| B | 只拔接收器 | 问题在 PS2 四线或接收器侧 |
| C | 只拔驱动那 8 根信号线 | 问题在驱动信号线侧 |
| D | 两者都拔，仍暗 | 短路在**板子/排针本身**（焊锡桥、被夹伤的走线） |

**第八次实测**：`BRINGUP_HALT_LEVEL = 3` + **接收器、驱动的线全部拔掉** → **灯正常亮起**。

→ 说明 PB12/PB13/PB14/PB15 这几个排针**没有对地/对电源短路**，GPIO 层空载时完全正常。
→ 注意：档位 3 时 PA0-3、PB6-9 仍是**高阻输入**（TIM 未初始化），所以**这次没有覆盖电机驱动那 8 根信号线**，必须用档位 4 才能覆盖。

**接下来的判定阶梯（每档重烧一次，烧完拔 ST-Link 再上 7.4V）**：

| 步骤 | 档位 | 接线 | 若变暗 → 结论 |
|---|---|---|---|
| ① | 3 | 只插接收器 | PS2 四线或接收器侧有短路/损坏（接收器被反接过也可能这样） |
| ② | 4 | 全部接上 | PA0-3/PB6-9 这 8 根信号线有短路；或驱动模块输入损坏；或驱动 VCC 误接到信号脚 |
| ③ | 5 | 全部接上 | 真正开始通信（CS 拉低、CLK 翻转）才触发 → 典型是 DAT/CMD 接反 |
| ④ | 6 | 全部接上 | PWM 通道启动后触发（占空比 0，正常不该有电流）→ 驱动输入侧问题 |

**第九次实测**：① 档位 3 + **只插接收器** → 灯变暗；② 档位 4 + 全部接上 → 灯也变暗。

→ **PS2 四线 / 接收器这一侧确实存在异常负载**（已把范围从"整个引脚层"缩到"PS2 四线"）。
→ 注意：② 因为接收器也接着，**不能**据此判定电机线有问题；要复核电机线，必须**拔掉接收器**再测档位 4。

**第十次补充**：接收器 VCC 接的是 **3.3V**（与 MCU 电平匹配，不存在 5V 上拉导致的额外电流），因此嫌疑收敛为"**线短路**"或"**接收器输入损坏**"两类。手头有**备用 4 芯线**，优先用替换法验证：

1. 停在档位 3，只插接收器，**换上备用线** → 正常 = 旧线内部短路（被夹破皮/插头扯松）；仍暗 = 接收器侧问题 → 做逐根线定位。
2. 定位到具体某一脚后，断电测**接收器该脚**对 GND/VCC 电阻：CMOS 输入应为高阻（>1MΩ）；若只有几欧~几十欧即为模块损坏 → 换接收器。

**第十一次实测（定位完成）**：档位 3 下**把接收器完全拔掉、只留线束插在板上，灯仍然是暗的**。

→ **负载在 PS2 线束本身，与接收器模块无关**。逻辑闭环：档位 2 时引脚高阻 → 不耗电（正常）；档位 3 时 PB14/PB15 被驱高、PB13 被驱低 → 线束内只要有**一根对 GND 短路**（或对 VCC 短路），就会有约 `3.3V / 驱动内阻 ≈ 几十 mA` 持续灌入 → 3.3V 轨塌陷 → 板上两颗灯与接收器灯同时变暗。

**处理顺序**：

1. **量线束**（两端都拔空，电阻档）：任意两根线之间、以及每根信号线对 GND 线 / VCC 线，正常都应**开路**。**边量边弯折、扭动线束** —— 压伤/断股的短路常常只在某个姿态下出现。
2. **直接换备用线**（最快）：停在档位 3 上电看灯。正常 → 旧线坏了。
3. 检查物理损伤点：线束是否被底盘/轮子/齿轮压过；插头压接处有没有铜丝搭接；两头排针焊点有无桥连；**板侧连接器有没有插错位（偏一针）**——偏一针会把 GND 落到信号脚上，直接造成上述短路。
4. 若换线后仍暗 → 逐根拔信号线（一次只插一根）定位到具体某根，再查该根对应的板侧排针。
5. **同时把电池充满到 8.4V** 再复测：低电量（6.5–7.0V）会把任何小异常放大成"灯暗"，充满后结论更可靠。



档位 3 时各线电平：`PB13(CMD)=低`、`PB14(CS)=高`、`PB15(CLK)=高`、`PB12(DAT)=输入上拉`。

| 接上哪根就暗 | 该线对外呈现 | 常见原因 |
|---|---|---|
| CMD（PB13，驱低） | 接到了正电源 | 线与 VCC 短路；接收器 CMD 输入损坏 |
| CS（PB14，驱高） | 接到了 GND | 线与 GND 短路（被夹破皮最常见） |
| CLK（PB15，驱高） | 接到了 GND | 同上；接收器 CLK 输入损坏 |
| DAT（PB12，输入） | —（只受内部上拉限制，不应变暗） | 若也变暗则说明另有短路 |

随后**断电**分别量：① 这根**导线本身**对 GND/VCC 的电阻；② **接收器排针**上该脚对 GND/VCC 的电阻。两者一对比就能区分"**线坏了**"还是"**接收器坏了**"。正常 PCB/接收器输入为高阻（>10kΩ；DAT 允许有 10k 级上拉）。

**逐级拔线定位**（每步上电看灯；用于确认外围支路是否另有问题）：

| 步骤 | 拔掉什么 | 若灯恢复正常说明 |
|---|---|---|
| 1 | 全部外围，只留 STM32 板（可改 USB 供电） | 问题在外围接线/短路，板子本身正常 |
| 2 | + 只接接收器 | 定位到 PS2 四根线（重点查 DAT/CMD 是否接反：PB12 必须输入） |
| 3 | + 只接 DRV8833 信号线（不接 VM） | 定位到电机驱动那 8 根信号线 |
| 4 | + 接 VM/电机 | 定位到电机电源侧 |

**压降定位（最有效，运行/灯暗状态下逐点量电压）**

原理：`压降 = 电流 × 串联电阻`。复位时电流几 mA → 压降可忽略；运行后电流升到几十 mA → 若路径上有高串联电阻，压降被放大，整条逻辑轨塌陷。所以**逐点量电压就能找出那一段坏的线/插针/焊点**。

黑表笔固定在电池负极，红表笔依次点（全部在"松开复位、灯已变暗"时量）：

```
电池正极 → 电池座/插头输出 → 导线末端 → 板子 5V 引脚 → 板子 3.3V 引脚 → 接收器 VCC
```

| 观察（同时记录串在电池正极的电流） | 结论 |
|---|---|
| 运行电流只比复位高几十 mA，但某相邻两点压降 >0.3V | **那一段导线/插针/焊点接触不良**（重做端子/重焊/换线） |
| 电流很小（<60mA），电池电压自己就从 4.0V 掉到 <3V | 电池放电/内阻大/保护板限流 → 充电或换电池 |
| 各点都正常，只有板子 3.3V 是 1–2V | **板载稳压器损坏** → 换板或外接 3.3V 稳压模块 |
| 运行电流比复位时高出**几百 mA** | 引脚短路/对顶（可能 MCU 或某模块已伤）→ 用上面的逐级拔线定位 |

**先做的两个免表测试**：① 只给 STM32 板接 USB、其余全拔 → 灯正常吗？② 只留 STM32 板 + 电池那一路 → 灯正常吗？两者对比即可区分"板子坏"还是"外围供电/接线坏"。

**需要记录的数字**：电池空载/带载电压、3.3V 轨电压（MCU 端与接收器端分别测）、空载总电流、断电时 VCC-GND 电阻、各模块温度。

**重点检查项**：

1. **电机电源必须从电池经 DRV8833 的 VM 取**，绝不能从 STM32 板的 5V/3.3V 输出取（板载 LDO 带不动电机，会直接被拉垮甚至永久损坏）。
2. 共地：电池负极、STM32 GND、DRV8833 GND、接收器 GND 必须同地。
3. 电源线/杜邦线/插针接触：轻晃线束看电压是否跳变（线阻分压会导致"灯暗"）。
4. 18650 电量与保护板：空载 <3.4V 基本放空；≈0V 且充不进 = 保护板跳闸。
5. 断电量 VCC-GND 电阻应 >100Ω，几十欧以下即为短路（查 DRV8833 输出、电机线、焊点）。
6. DAT/CMD 是否接反：PB12 必须是**输入**（接收器→MCU），PB13 是**输出**；接反会让两个输出对顶、持续发热耗流。
7. 上电时摇杆是否在中位：若手柄漂移或接收器欠压回乱码摇杆值，固件首帧就会接受并驱动电机 —— 排查时可先拔掉电机驱动 VM 再上电。
